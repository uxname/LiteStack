# LiteStack

## Проблема и цель

LiteStack — уже существующий и активно используемый полностековый шаблон
(backend liteend-go + frontend litefront, координация сверху).

Главная цель — **быстрый старт нового продукта**: auth, CI, деплой, доки
уже собраны. Остальные три — следствия этой:

2. Единый стандарт всех проектов: один стек, лёгкое переключение.
3. Сохранение накопленных лучших практик между проектами.
4. Витрина уровня инженерии.

Сверка с типовыми провалами шаблонов-стартеров и свежим аудитом показала:
ощущаемых болей нет, но аудит нашёл дыры там, где владелец смотрит реже
всего — тесты реальной аутентификации, вырезание секретов из логов, вес
первого экрана, утечка ресурсов при загрузке файлов. Первая итерация
улучшений закрывает именно их. Это гигиеническая итерация: её эффект —
сниженные риски, а не новые ощущения на старте.

## Пользователи и сценарии

- Автор проекта (ты) — использует активно, сам поддерживает и обновляет;
  проводит эту итерацию улучшений.
- Посетитель продукта, выведенного из шаблона — открывает первый экран;
  качество его опыта зависит от того, что шаблон кладёт в бандл
  (собранный комплект кода страницы).
- Оператор производного продукта — следит за сервером; корректность
  фоновых процессов шаблона определяет, деградирует ли он со временем.

## Что входит

- Тесты на вырезание секретов из логов (`redactSensitive`) и «пол
  покрытия» пакета logger — минимальная доля проверенного кода (60%),
  ниже которой проверка backend падает.
- Настоящие тесты проверки JWT (подписанного токена входа) на backend: истёкший токен, чужой издатель
  (issuer), чужая аудитория (audience) отклоняются; тесты идут без
  подставной аутентификации, ключи — локальный набор тестовых ключей
  (JWKS); допускается перекос часов серверов до ±60 секунд.
- Ленивая загрузка Sentry Session Replay (запись сеанса для отладки):
  её код не входит в первичный бандл; когда сессия попадает в выборку
  записи, запись начинается сразу, без перезагрузки страницы. Если
  подгрузка не удалась (Sentry недоступен), страница работает как раньше.
- Строка в документации шаблона о приватности записи сеансов: ввод
  посетителей маскируется (дефолт Sentry не отключаем), срок хранения и
  доступ к записям определяет владелец производного продукта своим
  планом Sentry.
- Фикс утечки при таймауте загрузки файла: остановленная запись завершает
  фоновый процесс и удаляет временный файл.

## Потом

- Проверка готовности шаблона к масштабируемости: что сломается при
  росте нагрузки, объёма данных и числа производных продуктов —
  заявленная тема следующей сессии.
- Сквозной тест (E2E) входа через настоящий поставщик входа (IdP) на
  frontend — тяжелее без CI.
- Автоматическая проверка полного цикла первого запуска из чистого
  клона — станет нужной при частых стартах или других пользователях.

## Что НЕ входит

- Подтягивание обновлений исходных шаблонов в уже выведенные продукты:
  производный проект — разовый снимок шаблонов и живёт своей жизнью
  (решение закреплено в OPERATING-MODE.md).
- Перенос улучшений этой итерации в уже выведенные продукты: они остаются
  со старым кодом, осознанно.
- Починка целостности самих проверок (автоисправление lint вместо падения,
  типовая проверка конфигов Vite, минимальные пороги покрытия пакетов
  middleware и server): текущее состояние принято окончательно.

## Ключевые истории

1. Как владелец шаблона я хочу, чтобы проверка ловила сломанное вырезание
   секретов из логов, чтобы чужие пароли не утекали в текстовые логи
   незаметно.
2. Как владелец шаблона я хочу настоящие тесты проверки JWT, чтобы дыра в
   проверке издателя или срока не уехала во все будущие продукты.
3. Как посетитель производного продукта я хочу быстрый первый экран, чтобы
   не скачивать ~122 КБ служебного кода записи сеанса, который нужен
   одному сеансу из десяти.
4. Как оператор я хочу, чтобы прерванная по таймауту загрузка файла не
   оставляла скрытых процессов и мусора, чтобы сервер не деградировал.
5. Как посетитель производного продукта я хочу, чтобы мой ввод не попал в
   запись сеанса в открытом виде, чтобы то, что я печатаю, осталось
   приватным.

## Критерии приёмки

1. Намеренно ломаем `redactSensitive` → проверка backend падает; пол
   покрытия logger 60% введён и действует.
2. Тест подаёт истёкший токен, токен чужого issuer и чужой audience → все
   три отклонены; тесты запускаются без подставной аутентификации.
3. Анализ состава собранного бандла: кода replay нет в точке входа;
   сессия из выборки записи начинает записываться сразу; при закрытой
   сети до Sentry первый экран работает как раньше. Команда анализа
   записана в документации.
4. Тест с падающим писателем: таймаут записи файла → фоновый процесс
   записи завершён, временный файл удалён.
5. В документации шаблона есть правило приватности: ввод посетителей
   маскируется, срок хранения записей и доступ к ним определяет владелец
   производного продукта планом Sentry.
6. Ручная проверка на свежем клоне: setup.sh и doctor.sh завершаются
   успехом — конфигурация `.env` читается настоящая, а не пример.

## Данные

Шаблон сам продуктовых данных не хранит. Его артефакты: конфигурация в
`.env` (контракт — docs/ENV-CONTRACT.md; проявляется в приёмке — ручная
проверка запуском setup.sh и doctor.sh), логи приложения, файлы из upload. Записи сеансов
посетителей уходят на серверы Sentry — третьей стороне; их правило в
«Что входит»: ввод маскируется, хранение и доступ — решение производного
продукта. Итерация новых данных не добавляет.

## Метрики успеха

Осознанно без метрик: итерация мала, критериев приёмки достаточно
(решение в «Решениях и отклонённом»).

## Ограничения и риски

- Документ ведётся на русском языке — осознанное исключение из правила
  репозитория English-only: это рабочий инструмент владельца.
- В проекте принципиально нет CI — решения не должны требовать его
  появления.
- Работа идёт в трёх репозиториях сразу (мета-репо + два сабмодуля);
  изменения нужно проводить согласованно.
- Возврат replay в первичный бандл при будущем обновлении Sentry не
  защищён автоматически — ловит следующий аудит.

## Решения и отклонённое

- PRD на русском, а не английском: скорость мышления владельца важнее
  единообразия репо для этого одного файла.
- Свежесть зависимостей — вручную, силами владельца: старты редки,
  автоматика (боты, календарь) не окупается.
- Автоматическая проверка первым же запуском отложена: ручная — по
  надобности.
- Дрейф доков ловим периодическим аудитом, а не автопроверкой команд и
  ссылок из доков.
- Из двух тестовых тем выбрана реальная аутентификация, а не целостность
  самих проверок: закрывает более дорогой риск.
- Главная цель — быстрый старт; единый стандарт, практики и витрина —
  следствия.
- Итерация делается без боли: риски из аудита реальны, даже если сейчас
  ничего не ощущается.
- Метрики не вводим: размеру итерации хватает критериев приёмки.
- Режим автоисправления lint и текущее состояние прочих проверок приняты;
  пункты об их починке сняты вовсе.
- Граница тестов входа — только модуль проверки токена на backend;
  учебная заглушка входа (OIDC, протокол входа) на фронте остаётся
  режимом разработки.
- Приватность записи сеансов фиксируем строкой в доках, а не проверкой
  настроек: дефолтное маскирование Sentry достаточно.
- Проверка «replay вне бандла» — одноразовое доказательство + команда в
  документации; постоянную автоматическую проверку не заводим, регрессию
  ловит аудит.
- Все пять пунктов объёма внедряются одним заходом; приёмка — критерии
  1–6, включая проходящие автоматические проверки обеих сторон (backend
  и frontend).

## Открытые вопросы

- Готовность шаблона к масштабируемости: как поведёт себя стек при росте
  нагрузки, объёма данных и числа производных продуктов — проверяем в
  следующей сессии.

Остальные известные пробелы закрыты либо осознанно отложены («Потом»,
«Решения»).
