# LiteStack

## Проблема и цель

LiteStack — уже существующий и активно используемый полностековый шаблон
(backend liteend-go + frontend litefront, координация сверху).

Цели — все четыре, ранжирование пока открыто (см. «Открытые вопросы»):

1. Быстрый старт нового продукта: auth, CI, деплой, доки уже собраны.
2. Единый стандарт всех проектов: один стек, одни приёмы, лёгкое переключение.
3. Сохранение накопленных лучших практик между проектами.
4. Витрина уровня инженерии для коллег, клиентов, сообщества.

Сверка с типовыми провалами шаблонов-стартеров и свежим аудитом показала:
серьёзных болей нет, но аудит нашёл несколько дыр там, где владелец смотрит
реже всего — тесты реальной аутентификации, вырезание секретов из логов,
вес первого экрана. Первая итерация улучшений закрывает именно их.

## Пользователи и сценарии

- Автор проекта (ты) — использует активно, сам поддерживает и обновляет.
- Посетитель продукта, выведенного из шаблона — открывает первый экран;
  качество его опыта зависит от того, что шаблон кладёт в бандл.
- Оператор производного продукта — следит за сервером; корректность
  фоновых процессов шаблона определяет, деградирует ли он со временем.

## Что входит

- Тесты на вырезание секретов из логов (`redactSensitive`) и «пол
  покрытия» пакета logger — минимальный процент тестов, ниже которого
  проверка backend падает.
- Настоящие тесты проверки JWT на backend: истёкший токен, чужой издатель
  (issuer), чужая аудитория (audience) должны отклоняться; тесты идут без
  мока аутентификации.
- Ленивая загрузка Sentry Session Replay: код записи сессий не входит в
  первичный бандл, подтягивается только когда сессия попала в выборку.
- Фикс утечки при таймауте загрузки файла: остановленная запись не
  оставляет фоновый процесс, открытый файл и мусор на диске.

## Потом

- Целостность самих проверок: lint должен падать, а не молча править;
  типовая проверка должна видеть конфиги Vite; полы покрытия для
  middleware/server. Полезно, не срочно.
- E2E-тест входа через настоящий IdP на frontend — тяжелее без CI.
- Автоматический смоук полного цикла первого запуска из чистого клона —
  станет нужным при частых стартах или других пользователях.

## Что НЕ входит

- Синхронизация производных проектов с апстримом: производный проект —
  snapshot fork и живёт своей жизнью (решение закреплено в
  OPERATING-MODE.md).

## Ключевые истории

1. Как владелец шаблона я хочу, чтобы проверка ловила сломанное вырезание
   секретов из логов, чтобы чужие пароли не утекали в текстовые логи
   незаметно.
2. Как владелец шаблона я хочу настоящие тесты проверки JWT, чтобы дыра в
   проверке издателя или срока не уехала во все производные продукты.
3. Как посетитель производного продукта я хочу быстрый первый экран, чтобы
   не скачивать ~122 КБ служебного кода, который нужен одному сеансу из
   десяти.
4. Как оператор я хочу, чтобы прерванная по таймауту загрузка файла не
   оставляла скрытых процессов и мусора, чтобы сервер не деградировал.

## Критерии приёмки

1. Ломаем `redactSensitive` намеренно → проверка backend падает; пол
   покрытия logger введён и действует.
2. Тест подаёт истёкший токен, токен чужого issuer и чужой audience → все
   три отклонены; тесты запускаются без `OIDC_MOCK_ENABLED`.
3. В собранном первичном бандле нет кода replay-интеграции; он появляется
   только при попадании сессии в выборку записи.
4. Таймаут записи файла → горутина завершена, временный файл удалён,
   место освобождено; подтверждено тестом.

## Данные

Шаблон сам продуктовых данных не хранит. Его артефакты: конфигурация в
`.env` (контракт — docs/ENV-CONTRACT.md), логи приложения, файлы из upload.
Итерация улучшений новых данных не добавляет.

## Ограничения и риски

- Документ ведётся на русском языке — осознанное исключение из правила
  репозитория English-only: это рабочий инструмент владельца.
- В проекте принципиально нет CI — решения не должны требовать его
  появления.
- Работа идёт в трёх репозиториях сразу (мета-репо + два сабмодуля);
  изменения нужно проводить согласованно.

## Решения и отклонённое

- PRD на русском, а не английском: скорость мышления владельца важнее
  единообразия репо для этого одного файла.
- Свежесть зависимостей — вручную, силами владельца: старты редки,
  автоматика (боты, календарь) не окупается.
- Автосмоук первого запуска отложен в пользу ручной проверки по надобности.
- Дрейф доков ловим периодическим аудитом, а не автопроверкой команд и
  ссылок из доков: список от аудита дешевле и надёжнее скрипта.
- Из двух тестовых тем выбрана реальная аутентификация, а не целостность
  гейтов: закрывает более дорогой риск; гейты едут в «Потом».
